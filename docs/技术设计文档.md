# 干活蜂群 · 技术设计文档（Design Doc）

> 文档版本：v1.0 ｜ 状态：评审稿 ｜ 日期：2026-10-23
> 关联文档：《干活蜂群改造方案-2026-10-23.md》（产品需求与决策记录，本文档不重复产品层内容，只落技术设计）
> 适用范围：服务器部署版（当前形态，见 ADR-007）的统一技术基线

## 1. 背景与目标

干活蜂群是一个「AI 公司」产品：用户（老板）在可视化办公室里组建小组、配置多个大模型 API、发布任务与方案；系统按工种调度大模型完成文案/调研/代码类工作，经审核员按老板标准把关后交付，并对每一次模型调用精确记账。

原型阶段已验证核心闭环（发任务→执行→审核→交付→记账）。本设计的目标是把原型升级为**可长期演进的工程基线**：

- 全栈 TypeScript，契约优先（前后端共享类型），模块边界清晰
- 本地优先：全部数据（含 API Key）存用户本机，不依赖任何云端服务
- 账务正确性：每一分钱消耗可追溯到任务、成员、小组与 API，账本不可篡改
- 可靠性：进程崩溃/重启不丢任务、不重复扣费
- 可扩展：待命成员近零成本，公司规模（组数/人数）增长不引起架构变更

非目标（本期不做）：多用户/权限体系、云端同步、移动端、7×24 服务端运行（由后续"引擎迁 VPS"里程碑承接）。

## 2. 需求摘要

### 2.1 功能需求（摘要，详见产品方案）
- 组织：公司—小组—成员三级；成员含工种、专属提示词、技能标签（能力卡）
- API 管理：多条 API 并存（预设 DeepSeek/OpenAI/Anthropic/自定义兼容），按组分配，公司默认兜底；至少一条可用 API 才能开工
- 任务系统：单任务与项目（方案下发拆子任务）；状态机驱动；审核打回/裁决
- 成本：按 API 真实用量记账到任务/人/组/API/项目；采购充值与余额；预算与并发闸门；总经理汇报
- 知识库：全公司共享资料，执行时检索注入，成果回流归档（二期向量检索）
- 设置后台：API 配置、组织管理、运行参数、数据管理（导入/导出/备份）

### 2.2 非功能需求
| 类别 | 要求 |
|---|---|
| 数据主权 | 数据只落本机；Key 不出现在日志与接口响应明文中（掩码） |
| 正确性 | 账本只追加不修改；金额以最小单位（厘）整数运算，展示层格式化 |
| 可靠性 | 任务状态迁移幂等；崩溃后执行中任务可回收重入队，不重复执行已完成阶段 |
| 性能 | 待命成员零模型调用；办公室页面 2s 轮询增量刷新；百人待命无压力 |
| 可维护性 | lint+typecheck+test+build 四道门禁全过才可交付；接口契约变更必须先改共享类型 |
| 可观测性 | 结构化日志（带 taskId/apiId 的请求链路）；账本即审计日志 |

## 3. 总体架构

```
┌────────────────────────────────────────────────┐
│  客户端（浏览器 / 后续 Tauri 桌面壳）             │
│  React + TypeScript + Vite                      │
│  办公室视图（DOM，后续 PixiJS）· 老板面板 · 成本中心 · 设置后台 │
└───────────────┬────────────────────────────────┘
                │ HTTP JSON（契约：packages/shared 类型定义）
┌───────────────▼────────────────────────────────┐
│  服务端（Node + TypeScript + Fastify）           │
│  api 层（路由/校验/错误结构）                     │
│  domain 层（组织/任务/审核/账本/知识库 纯业务逻辑） │
│  engine 层（调度队列/并发与预算闸门/崩溃恢复）     │
│  llm 层（Provider 适配器：OpenAI 兼容 / Anthropic）│
│  store 层（SQLite 仓储，迁移脚本管理 schema）     │
└───────┬───────────────────────────┬────────────┘
        │ SQL                       │ HTTPS（usage 归一化回账）
   ┌────▼─────┐              ┌──────▼───────────────┐
   │ SQLite   │              │ 各家大模型 API（多条）  │
   │ 本地单文件 │              │ DeepSeek/OpenAI/...  │
   └──────────┘              └──────────────────────┘
```

单向依赖：api → domain → engine/llm/store；domain 不依赖框架，可独立单测。前端只通过 shared 契约与后端通信，不直连数据库与模型 API（Key 永不下发到前端）。

## 5. 数据模型（SQLite）

核心表（字段只列关键项）：

| 表 | 关键字段 | 说明 |
|---|---|---|
| apis | id, name, provider, base_url, api_key_enc, model, price_per_m_milli, created_at | Key 加密存储；price 用整数（厘/百万 token）避免浮点误差 |
| teams | id, name, color, api_id(nullable→默认), created_at | 软删标记 deleted_at |
| members | id, team_id, name, role, prompt, skill_tags(json), color | 工种枚举：组长/研究员/文案/程序员/审核 |
| tasks | id, project_id(nullable), team_id, assignee_id, title, type, brief, status, result, review_note, reject_reason, reject_count, idempotency_key, created_at, claimed_at, finished_at | 状态见 §6 状态机；idempotency_key 防重复创建/重复执行 |
| projects | id, name, brief, team_id, client_name, status | 方案下发的项目制容器 |
| ledger_entries | id, task_id, team_id, api_id, stage(执行/审核/重做）, prompt_tokens, completion_tokens, total_tokens, cost_milli, created_at | **只追加（append-only）**，不提供 UPDATE/DELETE 接口 |
| purchases | id, api_id, amount_milli, created_at | 采购充值记录 |
| kb_entries | id, scope(company/team), team_id, owner_member_id, kind（提示词/资料/成果/标准）, title, content, tags, created_at | 知识库；二期加 embeddings 表 |
| settings | key, value(json) | 公司默认 API、并发上限、单任务预算、提醒阈值等 |

**余额不单独存可变字段**：API 余额 = Σpurchases − Σledger_entries（该 API），由视图/查询推导，杜绝"账本与余额对不上"。任务总耗、小组排行、项目总账同理由 ledger 聚合，tasks 表不冗余存金额（仅缓存 total_tokens/total_cost_milli 供列表性能，须与 ledger 同事务更新）。

迁移：schema 用编号迁移脚本管理（migrations/001_init.sql …），启动时自动执行未应用项，禁止手工改库结构。

## 6. 核心状态机（任务生命周期）

状态：`pending（待领取） → running（执行中） → reviewing（待审核） → done（已完成）`，异常分支：`rejected（被打回）`、`adjudication（待裁决）`、`blocked（停工，附 blocked_reason）`。

| 迁移 | 触发者 | 守卫条件 |
|---|---|---|
| pending → running | 调度引擎 | 所属组 API 有 Key 且余额 > 0；全公司 running 数 < 并发上限；单任务累计 token < 预算上限 |
| running → reviewing | 执行成员完成产出 | 产出非空；本次调用已回账 |
| reviewing → done | 审核员判定通过 | 审核结论含逐条要点核对结果 |
| reviewing → rejected | 审核员判定不通过 | 必须附 reject_reason（引用具体要点）；reject_count+1 |
| rejected → running | 调度引擎 | reject_count < 2，工人按打回意见重做 |
| rejected → adjudication | 系统 | reject_count ≥ 2 自动转裁决；或预算超限在任意阶段直接转裁决 |
| adjudication → done | 老板裁决通过 | 记录裁决人=老板、裁决时间；裁决不受预算闸门拦截 |
| 任意 → blocked | 引擎检测 | API 无 Key/余额耗尽/连续调用失败熔断；条件恢复后自动回 pending |

状态迁移必须经 domain 层统一函数（校验合法迁移+守卫），禁止各处直接改 status 字段。项目状态由子任务聚合：全部 done → 项目 done（已交付）。

**M5 扩展（业务流程补全一期）**：状态枚举新增终态 `cancelled（已取消）` 与三条老板手动操作（均经 domain 层 cancelTask/retryTask/deleteTask 校验，不直接改 status）：
- **取消**：`pending / rejected → cancelled`；`reviewing` 仅在带 blocked 覆盖层（审核调用失败停工）时可取消。`running`（正在调用模型）、`adjudication`、`done` 不可取消。取消写 finished_at 并清 blocked 覆盖层。
- **重试**（清停工）：仅带 blocked 覆盖层的任务可手动重试——清 blocked_code/blocked_reason 后任务回到队列，引擎按其当前状态继续（待领取→重新执行、被打回→重做、待审核→续跑审核）。`cancelled` 终态不可重试；未停工任务（含执行中/审核中/已完成）拒绝并回 VALIDATION。
- **删除**（非状态迁移，是记录移除）：仅 `done / cancelled` 可删；只删 tasks 行，**ledger 行保留不删**（删任务不删账，余额推导与按 API/小组聚合不受影响）。
- 项目聚合口径随之扩展：已取消子任务为终态、不阻塞「已交付」判定（全部未取消子任务 done 且至少一个 done → 已交付；全部子任务被取消时保持进行中）。

## 7. API 契约（REST，节选）

契约优先：请求/响应类型先在 `packages/shared` 定义，前后端共同引用；接口变更先改类型再改实现，CI 类型检查兜底。

| 方法与路径 | 说明 |
|---|---|
| GET /api/state | 办公室全量状态快照（组织+任务+账本聚合），前端轮询 |
| POST /api/tasks | 发布任务（title/type/brief/teamId/projectId?） |
| POST /api/projects | 下发方案（name/brief/teamId/clientName）→ 组长拆子任务 |
| POST /api/tasks/:id/adjudicate | 老板裁决通过 |
| GET/POST /api/settings/apis | API 列表（Key 掩码）/ 新增修改（Key 留空=不改） |
| POST /api/settings/apis/:id/purchase | 采购充值 {amount} |
| POST /api/settings/teams、/members | 组织与成员维护（含专属提示词、技能标签） |
| POST /api/settings/review-standards | 审核要点 + 甲方需求 |
| GET /api/cost/report | 总经理汇报数据（聚合：组/API/项目排行、最贵一单、余额续航估算） |
| GET/POST /api/kb | 知识库条目查询/新增（含 scope 与 tags） |
| POST /api/members/save（M5） | 成员新建/编辑/换组 `{ member:{ id?, name, role, teamId, prompt } }`；工种变更时人设重置为该工种默认 |
| POST /api/members/delete（M5） | 删除成员；守卫：名下有未完成任务（状态 ∉ 已完成/已取消）时拒绝，回 `MEMBER_HAS_ACTIVE_TASKS` |
| POST /api/apis/test（M5） | 测试连接：入参 `{ id }` 或 `{ api:{ provider, baseUrl, model, apiKey } }`（apiKey 留空且有 id 时回退已存 Key）；直连 Provider 发一次最小 chat（max_tokens=1、超时 15s），**不走网关、不记账、不扣余额、不触发熔断**；返回 `{ ok:true, test:{ ok, latencyMs, message } }`，失败 message 为厂商错误原文摘要 |
| POST /api/tasks/:id/cancel、/retry、/delete（M5） | 任务后悔药，合法性口径见 §6 M5 扩展；delete 仅删任务行、账本保留 |
| GET /api/backup（M5） | 数据备份下载：先 `PRAGMA wal_checkpoint(TRUNCATE)` 合并 WAL，再以附件形式返回当前 SQLite 单文件 |

统一错误结构：`{ ok:false, error:{ code, message } }`，错误码在 shared 中枚举（VALIDATION / NO_API_KEY / INSUFFICIENT_BALANCE / BUDGET_EXCEEDED / PROVIDER_ERROR …）。入参一律 zod 校验，校验失败不进 domain。

## 8. LLM 适配层

统一 Provider 接口（llm 层），业务代码不感知厂商差异：

```ts
interface LlmProvider {
  chat(req: { model: string; system: string; messages: Msg[] }): Promise<{ text: string; usage: Usage }>
  review(req: { model: string; standards: Standards; draft: string }): Promise<{ pass: boolean; reason: string; usage: Usage }>
  embed?(texts: string[]): Promise<{ vectors: number[][]; usage: Usage }>  // 二期知识库向量
}
interface Usage { promptTokens: number; completionTokens: number }  // 归一化后的统一口径
```

实现：OpenAiCompatibleProvider（DeepSeek/OpenAI/自定义，/chat/completions）、AnthropicProvider（/v1/messages）。横切要求：
- 每次调用必回 Usage 并同事务写 ledger；厂商未返回 usage 时按文本长度估算并在 ledger 标记 estimated
- 超时（默认 120s）+ 失败重试：仅对网络错误/5xx/429 指数退避重试（最多 2 次），4xx 业务错误不重试；重试不重复记账（按调用幂等键）
- 审核返回强制结构化（JSON），解析失败有兜底：提取 pass/reason 失败 → 视为不通过并附原始结论，避免脏数据蒙混过关
- 同一 API 连续失败 ≥3 次熔断 5 分钟，期间其任务转 blocked 并注明原因

## 9. 调度引擎

- 内存队列 + 数据库状态双写：以 DB 为准（进程重启可恢复），内存队列仅作加速
- 轮询 tick（1s）扫描 pending：按创建时间 FIFO，逐个过守卫（Key/余额/并发/预算），满足才领取
- 工人执行与审核是两次独立 Provider 调用，中间落库 reviewing，任一阶段崩溃可从该阶段续跑，不重跑已回账阶段
- 崩溃恢复：启动时扫描 running/reviewing 超时任务（>10 分钟无心跳）→ 回 pending 并记录恢复日志
- 并发闸门与预算闸门参数来自 settings，修改即时生效

## 10. 知识库设计

- 一期（随工程基建后第一个增量）：kb_entries 全量可见（公司级+小组级），执行时注入策略 = 公司标准全文 + 与任务标题/类型关键词命中的资料条目（上限按 token 预算裁剪）；成果 done 后自动以 kind=成果 回流入库
- 二期：embeddings 表（entry_id, chunk, vector），保存条目时经所配 API 生成向量，检索改余弦相似度 Top-K；向量与条目同存本地 SQLite，不依赖外部向量服务
- 注入必须可审计：任务详情记录本单实际注入了哪些条目（ids），便于复盘"为什么这么写"

## 11. 安全

- 服务只监听 127.0.0.1，不对局域网/公网开放
- API Key：存储加密（机器派生密钥加密落盘）；日志、错误信息、接口响应一律掩码（只留后 4 位）
- 前端永不持有 Key：所有模型调用经服务端转发
- 导入 JSON 数据包时做结构校验，拒绝含可执行内容的字段直入

## 12. 可观测性与测试策略

- 日志：结构化 JSON 行日志（ts/level/module/taskId/apiId/msg），按天滚动存 data/logs；账本即资金审计，不另设审计表
- 测试分层：
  - 单元（Vitest）：金额换算与余额推导、状态机合法迁移与守卫、Provider 响应解析（含 usage 缺失、审核 JSON 脏数据）
  - 集成：对 mock-llm 跑完整流水线（发单→完成→账本对账→余额扣减→打回/裁决分支）
  - 冒烟：构建产物起服务，首页与关键接口 200
- CI 门禁（GitHub Actions）：install → lint → typecheck → test → build，五步全绿才允许打版本 tag
- 发布：语义化版本（SemVer），CHANGELOG 记录每个版本的功能/修复/破坏性变更，源码包与运行包分开产出

## 14. ADR 摘要（决策记录，全文见 docs/adr/）

- ADR-001 桌面端本地优先：数据主权与 Key 安全优先于多端便利；代价是无 7×24，后续以"引擎迁自有 VPS"补齐
- ADR-002 多 API 并存：按组分配、默认兜底；至少一条可用才开工
- ADR-003 全栈 TypeScript：与负责人技能栈（JS）和原底座（AI Town）一致，前后端共享契约
- ADR-004 SQLite 单文件存储：本地单机场景足够，零运维；账本 append-only + 余额推导保证对账
- ADR-005 Muse 本人当发动机仅为过渡形态（真干活版验证闭环），正式引擎为用户自配 API，不构成产品依赖

## 15. 决策补充（2026-10-23 Muse 拍板，实施以此为准）

### 15.1 模型相关
- **调用温度**：执行（工人产出）0.7；审核 0.1（判定要稳定一致）；组长拆单 0.3；后续如需可配，先写死为常量并集中定义。
- **模型分工**：API 条目自带 model 字段即该线路的执行模型；审核默认同线路模型但以低温度调用。预设默认模型名仅作占位引导（deepseek→deepseek-chat、openai→gpt-4o-mini、anthropic→claude-sonnet 系列），以用户填写为准。
- **审核判定口径**：硬要点（"必须包含/禁止/不超过 N 字"类可机检项）不满足必打回；其余要点由审核模型综合判定，结论必须逐条引用要点。审核返回解析失败按不通过处理（见 §8）。
- **超时与重试**：单次调用超时 120s；仅网络错误/5xx/429 指数退避重试 ≤2 次，退避基数 1s；4xx 不重试。重试沿用同一调用幂等键，不重复记账。
- **熔断**：同一 API 连续失败 ≥3 次熔断 5 分钟；熔断期满进入半开，先放行 1 单试探，成功则恢复、失败则再熔断 5 分钟。
- **usage 缺失估算**：按字符数粗估（中文约 1 字≈1 token、英文约 4 字符≈1 token），ledger 标记 estimated=true，汇报中单独标注估算占比。
- **上下文裁剪**：知识库/历史注入总量上限为该任务剩余预算的 30%（无预算上限时取固定 8k token 上限），按"公司标准 > 本组资料 > 他组资料 > 历史成果"优先级截断。
- **embedding（二期）**：走所配 API 的 embedding 接口，模型名随 API 条目配置，未配置 embedding 的线路不参与向量检索（回退关键词注入）。

### 15.2 状态机补充
- **心跳与回收**：running/reviewing 任务每 30s 更新心跳；>10 分钟无心跳判定失联，启动/巡检时回收回 pending 并写恢复日志（见 §9）。
- **blocked 恢复**：守卫条件恢复（充值/补 Key/熔断结束）后自动回 pending 重排，不需人工干预；blocked_reason 保留最近一次原因直至成功领取。
- **排队顺序**：一期严格 FIFO（按 created_at）；优先级队列列入二期，本期不实现。
- **裁决的统计口径**：老板裁决通过的任务计入成员"完成数"，但单独标注「裁决通过」，不计入审核一次通过率；总经理汇报单列待裁决与裁决通过数量。
- **项目聚合**：子任务全部 done → 项目已交付；任一子任务进入 adjudication → 项目状态显示「待裁决」；项目总账为子任务 ledger 之和加拆单调用那笔（记在项目 id 上）。M5 扩展：已取消子任务不阻塞已交付判定（口径见 §6 M5 扩展）。

- **署名保留口径（B/F 共用）**：平台库公示署名一律「快照优先」——skill 在管理员 approve 上架时、风格模板在管理员 approve 上架时，把 contributor_name / contributor_workspace_name 写入行内快照；源用户/空间注销或改名后署名以快照保留、不悬空。存量数据的兼容投影（contributorOf）：快照非空优先；无快照（platform 官方）回 null；其余回退实时查用户/空间现名，再无则「已注销用户/已注销空间」。官方自研内容（owner_type='platform'）不带署名、只标「官方」，与用户贡献分开展示。
- **精选口径（B）**：featured 是管理员对「已上架（visibility='public'）的用户 skill」的二次策展标记，与上架审核是两个独立动作：仅 public 可精选、晋升/取消均写审计（admin_feature_skill / admin_unfeature_skill）并经新通知类型 skill_featured / skill_unfeatured 通知贡献者空间；精选幂等（状态无变化不重复通知）。安装量口径 = skill_installations 行数实时计数，不设冗余列；「最新动态」为 listed_at 与 featured_at 两类事件的服务端合并投影（GET /api/skills/activity）。
- **弹窗外壳与深链口径（E）**：办公室（PixelOffice 场景页）是登录后的唯一主场景；功能面（publish/tasks/projects/results/skills/assets/kb/cost/schedules/settings/member/style）全部以 Radix Sheet 弹窗承载，既有页面组件整体复用为弹窗内容。深链约定 `#/<dialog>`（member 为 `#/member/<id>`），关闭即清回 `#/`；hash 写入与弹窗状态用抑制旗双向同步、防回环。实况数据一律派生自真实 state：状态栏余额 = Σ apis.balanceYuan、进行中 = 状态为「执行中」任务数、待审核/待裁决同理；成员动画相位由成员任务状态驱动（仅在既有 rAF 循环内加位移，无新增动画系统）。登录/注册、管理台、帮助、账号、公开交付页、参观页按例外清单保持独立页。移动端弹窗全屏、内部滚动，全站 0 横滚基线（§18）不变。
- **风格槽位与图片公示（F）**：风格配置 JSON 存 settings 键 officeStyle（palette/floorPattern/furniture/poster/sign 五键）；家具为九个预设锚点槽位（plantLeft/plantRight/sofa/bookshelf/fishtank/rug/painting/coffee/cat），每槽位仅选款/开关、不做自由坐标；未知款式键渲染层回退默认款、显式 null 或缺键即不绘制。上传图片落 DATA_DIR/style-images/ 并以 index.json 登记归属空间，读取端（GET /api/style-images/:fileId）按「本空间 / 被 public 风格模板引用」判定可见——**未过审图片不公示**是服务端硬约束而非前端隐藏。风格模板三级 visibility（private/workspace/pending_review→public）与管理员审核状态机复用 skill 上架的口径；apply 为整体覆盖 + apply_count 自增；「一键生成搭配」是站内预设和谐随机组合，不接生图模型，文案与本节均不称 AI 生成。默认风格与 v1.2.0 画布像素级一致是集成定案（floorPattern='checker'、furniture={plantLeft:'green', plantRight:'green'}）。
- **晨报昨日口径与邮件接入点（G）**：晨报「昨日未完成」= created_at 早于空间时区今日 00:00 且状态非终态的任务全集（进行中/待审核/待裁决/被打回四组 + 「曾被打回 reject_count>0」重叠计数单独一行），空间时区取 settings.timezone（缺省 Asia/Shanghai），与 G-10 定时任务共用同一组时区换算函数，不另写第二份。签到 streak 口径：今日已签则含今日、未签则截至昨日，断一天即断。调度为独立 30s tick（runDailyTick 导出供进程内测试），签到提醒靠 checkinRemindedDate 标记 + 同类未读通知去重双保险只发一次；晨报生成以 briefings（workspace,date）唯一键幂等。**邮件接入点**：晨报与签到提醒的邮件分支统一收口在 notify.ts 的 maybeMailDaily 空实现——复用 v1.2.0 预留的 notifyConfig/mailChannel 结构，未配置 SMTP 时 mailStatus 恒为 'not_configured' 且静默跳过；设置页如实展示该状态。SMTP 通道（G-01）落地时只填这一处实现，不另起发信路径。热点新闻抓取在服务端完成（公开 RSS、主题→双源映射、5s 超时），失败或无条目整段降级为「今日热点暂不可用」，生成侧禁止编造新闻内容。
- **问卷生成与不重组原则（C2）**：问卷是开空间流程的扩展而非新通道——POST /api/workspaces 带 questionnaire 段时依次建空间、teamForge 生成团队（替代默认种子）、建 API 设默认、存问卷、写提醒设置，forge 失败自动降级默认种子并在审计 detail 注明，空间永不因问卷半途失败而残缺。teamForge 以「行业包 manifest（parseManifest 直读）× 职能模板库（内置映射）」拼装普通 teams/members：模板覆盖当前唯一行业包 short_drama 的四职能（内容生产/学习研究/日常办公/运营推广）与通用兜底四职能，工种须经 listRolesVisible 校验、人设按（行业，工种）模板拼装、全字段非空由测试锁定。**不重组原则**：问卷只在建空间时生成一次；已有团队的空间不自动重组；PUT /api/questionnaire 仅更新存档与提醒设置（同步 dailySettings），其 payload 中的 api/apiKey 一律忽略——绝不碰 apis 表、绝不重组团队。API 步的 Key 只经既有写路径落 apis 表（加密存储），问卷表仅存 provider/baseUrl/model/apiId/keyMasked，不留明文。测试连接走 POST /api/apis/test-connection 裸配置端点，与设置页共用 domain/apiTest.ts 实现，失败回厂商原文、不吞错误。服务商预设的唯一源为 shared PROVIDER_PRESETS；前端向导的初始值常量与之逐项同值（web 无法值导入 shared 的 CJS 桶文件，属已知构建口径）。
- **任务模板三级与官方种子（A3）**：task_templates 以 workspace_id 可空区分官方（NULL）/行业（NULL + industry_pack_id）/个人（空间 id）三级，可见集 = 官方 ∪ 本空间所选行业包 ∪ 本空间自建；删除仅限本空间自建，其余 404。行业模板的 pack id 存在两种写法（种子写 'short_drama'、空间 industry_pack_id 写 'pack_short_drama'），仓储层以子查询别名解析双向匹配，属兼容口径、非数据错误。套用仅预填发单表单（useTemplate），不产生任务。模板上架/分享本版明确不做，分享路径由 skill 生态（B）与风格模板（F）覆盖。
